# Deploying TechPro+ CRM

Two supported paths: **Render** (recommended — flat pricing, backups
included from the cheapest paid tier) or **Railway** (usage-based
pricing, backups gated to the Pro plan). Both need the same two secrets
generated once, up front.

---

## Before either platform: generate your two secrets

Run these locally (needs Python + the `cryptography` package — already
in `requirements.txt`, or just run `pip install cryptography` first):

```bash
# SETTINGS_ENCRYPTION_KEY — encrypts SMTP/Twilio credentials at rest in the DB
python3 -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"

# SESSION_SECRET — signs staff login session cookies
python3 -c "import secrets; print(secrets.token_hex(32))"
```

Save both output strings somewhere safe (a password manager). You'll
paste them into the platform's dashboard in a moment. **Never commit
these to git or put them in `render.yaml`/`railway.json`** — that's
why both config files leave them as manually-set secrets rather than
hardcoding them.

---

## Option A: Render (recommended)

1. Push this repo to a GitHub repo (private is fine).
2. In the Render dashboard: **New +** → **Blueprint** → connect the repo.
   Render reads `render.yaml` automatically and shows you a preview of
   what it's about to create: one web service + one Postgres database.
3. Click **Apply**. Render provisions both and wires `DATABASE_URL`
   from the database to the web service automatically — you don't type
   a connection string anywhere.
4. Once the service exists, go to its **Environment** tab and add the
   `SETTINGS_ENCRYPTION_KEY` you generated above (`SESSION_SECRET` is
   already auto-generated by the blueprint — leave it alone).
5. Redeploy (Render prompts you to after adding the env var).
6. Visit the service's `.onrender.com` URL. A brand-new database opens the
   **first-run setup** page (see "v51 first-run setup" below): it asks for the
   one-time setup code from the service's **Logs** tab, then your shop name,
   province and your own PIN. There is no default PIN any more.

**Cost:** ~$13/mo flat (Starter web $7 + Basic-256mb Postgres $6).
Point-in-time recovery is included at this tier.

**Custom domain:** Render → your service → Settings → Custom Domains.
Free, just point a CNAME at the `.onrender.com` address.

## Option B: Railway

Railway doesn't support one-file blueprint provisioning the way Render
does, so the database and secrets are added through the dashboard:

1. Push this repo to GitHub.
2. Railway dashboard → **New Project** → **Deploy from GitHub repo** →
   select this repo. Railway auto-detects the `Procfile` and
   `runtime.txt` and builds it (`railway.json` in this repo pins the
   health check and restart policy on top of that).
3. In the same project: **+ New** → **Database** → **Add PostgreSQL**.
4. Click into your web service → **Variables** tab → **+ New Variable**
   → **Add Reference** → select the Postgres service's `DATABASE_URL`.
   This wires them together without you copy-pasting a connection
   string.
5. Still in Variables, manually add:
   - `SESSION_SECRET` = (the value you generated above)
   - `SETTINGS_ENCRYPTION_KEY` = (the value you generated above)
6. Deploy. Railway gives you a `.up.railway.app` URL — visit it and finish the
   **first-run setup** (setup code from the service's **Deploy Logs**, see
   "v51 first-run setup" below). There is no default PIN any more.

**Cost:** $5/mo Hobby plan minimum, but realistically **$10–20/mo**
once actual usage is billed on top of the included credit — this is
metered, not flat, so it moves month to month. **Automated backups are
Pro-plan-only ($20/mo min)** — on Hobby, either add Railway's
one-click "Postgres Daily Backups" template yourself, or accept the
risk. This is the main reason Render is the default recommendation
above.

## Either platform: the health check

Both configs point at `GET /healthz`, which returns `{"status": "ok"}`
without touching the database or requiring login — deliberately so a
briefly-reconnecting DB doesn't cause a false-negative restart loop.

## Either platform: what NOT to do

- Don't set `SETTINGS_ENCRYPTION_KEY` to Render's auto-generated
  value or any random string typed by hand — it must be a real Fernet
  key from the command above, or the app silently falls back to
  storing SMTP/Twilio credentials **unencrypted** rather than erroring
  loudly. This is why `render.yaml` deliberately does *not* use
  `generateValue: true` for that one variable.
- Don't lose the `SESSION_SECRET`/`SETTINGS_ENCRYPTION_KEY` values once
  set — rotating `SETTINGS_ENCRYPTION_KEY` makes any already-encrypted
  settings (SMTP password, Twilio token) undecryptable; you'd need to
  re-enter them in Settings after a rotation.


## v48 security variables (optional)

- `CLIENT_IP_HEADER` — only if you host somewhere other than Railway: the request header that carries the visitor's
  real address (for example `x-forwarded-for`). The wrong-PIN wait is counted per address; without this on another
  host every visitor can look like the proxy. Railway needs nothing.
- `RESET_2FA=1` — emergency only. Lost the phone **and** the recovery codes for the Owner? Set this, restart, sign in
  with your PIN, then **remove the variable** (it switches 2-step off at every start while it is set).
- `BACKUP_EMAIL_MAX_BYTES` — size limit for the weekly backup email (default 3500000, because the email service
  refuses 4 MB attachments).
- Keep `SETTINGS_ENCRYPTION_KEY` the same on any server you restore a backup onto; saved passwords, API keys and
  authenticator secrets are encrypted with it.


## v49 repair photos (no new variables)

- Photos are stored **in the database** (a new `repair_photos` table), not as files, so they survive a redeploy and need
  no extra storage service. The phone shrinks each picture to about 200 KB first, so 1,000 photos is roughly 200 MB.
  On Railway watch the Postgres volume size if you take many photos; **Settings → Data → Download all repair photos**
  gives you a .zip you can keep elsewhere.
- Photos are **not** inside the Full Backup file (they are too big for it). A restore keeps the photos of tickets that
  are in the backup and deletes the photos of tickets that are not; the restore screen tells you the numbers first.
- The camera needs the page to be served over HTTPS (Railway does this). Nothing about the security headers changed.


## v50 camera scanning and stock counts (no new variables)

- **The camera needs HTTPS.** Railway serves your app over HTTPS, so nothing to do. If you run it on an office computer
  over plain `http://`, phones will refuse to open the camera (the scanner then offers a box to type the number).
  `http://localhost` is fine for testing.
- The barcode reader for iPhone is `static/vendor/zxing-library-0.23.0.min.js`, served by your own app; the content
  security policy still forbids loading code from anywhere else. Chrome on Android uses the phone's built-in reader.
- Two new tables (`stock_counts`, `stock_count_lines`) and one new column (`products.barcode`, indexed) are created on
  the first start. Nothing existing is changed; products simply start with an empty barcode.
- Stock counts are inside the Full Backup file. A backup made by v49 or earlier restores fine (products get an empty
  barcode, there are no counts).


## v51 first-run setup (a second shop, or a copy for someone else)

A **brand-new, empty database** no longer starts with the PIN `1234`. Instead the site stays locked on one page,
`/setup`, until the owner claims it. Nothing else on the site opens (apart from `/healthz`, which the host's health check
needs).

1. Deploy as above (own database, own `SESSION_SECRET` and `SETTINGS_ENCRYPTION_KEY`: never share these between shops).
2. **Find the setup code.** On start-up the server prints a block like `SETUP CODE: K7QM-4TRD-X9WB` into its log
   (Render: **Logs**; Railway: **Deploy Logs**). Or choose your own by setting the variable `SETUP_CODE` (at least 6
   letters/digits) before the first start; the log then says to use that variable and never prints it.
3. Open the site, type the code, then the shop name, the **province** (this sets the tax: Alberta is 5% GST only,
   BC is 5% GST + 7% PST) and the owner's own **PIN (6 to 8 digits, numbers only; obvious ones such as 123456 are
   refused)**. You are signed in and land on the **Help** page.
4. The sample products and customers that come with a fresh database are removed by default (a tick-box keeps them).
5. After setup the code is deleted. A start-up that finds staff already in the database never shows setup, so an
   existing shop (such as the Vernon store) is **never** affected by this change, and restoring a backup onto a new
   server brings that shop's own staff and PINs with it.

**The lock stays on until setup is finished**, so do step 3 right after the first deploy rather than leaving a new site
sitting open with a visible code in its log.

## v51 other notes

- No new packages and no new required variables. One column (`stock_count_lines.reason`, plus a frozen `unit_cost`) is
  added automatically on start-up.
- The phone camera (barcode and IMEI scanning) still needs **HTTPS**, which Render and Railway both provide.
- Help for staff is at **/help** (the "Help" link at the top of every page): selling, repairs, trade-ins, scanning,
  stock counts, closing the till and staying safe, written for the cashier on duty.


## v52 release notes for the host (no new packages, no new required variables)

- **Back up first** (Settings → Data → Download Full Backup), then replace the files and restart. On the first start four
  tables are created (`sale_returns`, `sale_return_lines`, `expenses`, `quote_approvals`) and one column
  (`cash_sessions.paid_out`) is added. Existing data is untouched; Postgres on Railway needs no manual step.
- **Quote links** (`/q/<code>`) are public by design: the long random code is the key and the page shows only the shop
  name, ticket number, device, work and price. They are built from the address the staff member opened the CRM from
  (always `https://` on Render/Railway), so staff should send quotes from the real shop address, not a local one. If you
  put the app behind your own domain, nothing else needs setting; `CLIENT_IP_HEADER` (see v48) makes the "too many wrong
  codes" slow-down count per visitor rather than per proxy.
- **Quote texts use Twilio** (Settings → Notifications). With no Twilio set up, the ticket offers **Just make the link**
  instead and the owner can send the link another way.
- **Camera scanner on a real phone:** open **/scanner-test** (Help → *Test the scanner on this phone*) on each phone that
  will scan, using the https address. It is the only check that can prove the lens works; see CHANGES_v52.md.
- Returns, expenses and quote approvals are inside the **Full Backup** and are restored with it. A backup made by v51 or
  earlier restores fine (it simply has none of them).
